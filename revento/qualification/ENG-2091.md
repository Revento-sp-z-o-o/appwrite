# ENG-2091: document caches after the outer transaction

Concurrent signup status reads exposed a committed row reported as `processing`
by document GET while list returned `succeeded`. A standalone synthetic API race
reproduced the mismatch after a successful 200-row commit: user/admin GET returned
generation 1, list returned generation 2. It reproduced on the first attempt;
commit took 5.669 seconds. The fixture was removed after evidence capture.

Native PostgreSQL tests with independent pooled connections reproduce the same
failure on pinned upstream Utopia 7.3.4 and the previously deployed maintained
build. Six cases failed: update, permission revocation, delete, counter, create
negative cache and bulk update. Rollback control passed. This rules out the SDK,
client polling cache and the earlier transaction relationship optimization as
necessary causes.

## Change

Nested database mutations invalidate document cache before the enclosing SQL
transaction commits. An independent reader can repopulate the previous committed
value during that window. Record resolved document/collection cache keys while a
transaction is open and invalidate them again when the outermost transaction
ends. Keep immediate purges, deduplicate final purges and clear pending state
before cleanup. Attempt each purge independently, continue other keys after an
error and preserve the original transaction error on rollback.

A cache failure after SQL commit is logged, while preserving the successful SQL
result so Appwrite can finalize transaction status and dispatch events. The original
rollback exception is also preserved. Any failed document purge, including a
transient single-key failure, can retain stale values/ACLs; this patch cannot
guarantee freshness when invalidation fails. No blanket cache flush or change to
transaction operations, SDKs, SQL isolation, events or relationship options.

## Remaining scope

ENG-2092 tracks a distinct pre-existing isolation problem: an ordinary writer
getDocument inside an open transaction can cache an uncommitted value/temporary
ACL grant. ENG-2091 repairs that cache on outer completion, but does not prevent
its publication during the transaction. Library reachability is reproduced;
public API exploitability has not been established.

This is not signup throughput qualification. Rerun focused 20- and 242-user
measurements after dev2 activation, then diagnose remaining queue/commit latency.
No production readiness, customer-data import, DNS change or cutover is implied.

unique per run. Never point these fixtures at a shared non-test database.
